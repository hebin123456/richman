# 测试文档

本文档说明本项目当前的测试策略、执行方式、补测原则和提测前检查项。

## 1. 测试目标

本项目的测试目标不是“把所有实现都重复写一遍”，而是优先覆盖这些高风险点：

- 服务端规则是否按预期修改权威状态
- 复杂数值规则是否回归
- 新棋盘格、新道具、新神明、新牌组是否接线完整
- 托管 / 机器人是否能在新规则下继续行动
- 页面在接到快照后是否能展示关键结果

## 2. 当前测试类型

### 2.1 自动化单元测试

当前使用：

- Vitest

主要分布在：

- `src/lib/game/*.test.ts`

当前覆盖的模块包括：

- `board`
- `autoplay`
- `news-house`
- `gods`
- `map-gods`
- `travel-gods`
- `economy`
- `calendar`
- `shop`
- `dice`
- `room-expiration`
- `lottery`
- `cards`（新增后建议持续维护）

### 2.2 手工测试

由于项目包含 Phaser 表现层、SSE 同步和多阶段 HUD 弹窗，部分内容更适合手工验证：

- 棋子动画
- HUD 面板与弹窗层级
- 房间多人同步体感
- 事件快报是否正确自动弹出
- 托管节奏是否自然

## 3. 如何执行测试

### 3.1 运行全部自动化测试

```bash
npm test
```

### 3.2 运行单个测试文件

```bash
npm run test -- src/lib/game/cards.test.ts
```

### 3.3 监听模式

```bash
npm run test:watch
```

### 3.4 构建验证

```bash
npm run build
```

### 3.5 Lint

```bash
npm run lint
```

## 4. 推荐测试流程

### 4.1 规则改动

如果改的是：

- 道具
- 神明
- 机会 / 命运
- 监狱 / 贷款 / 通胀
- 新闻屋 / 彩票 / 商店

建议顺序：

1. 先补或更新单元测试
2. 跑目标测试文件
3. 跑 `npm run build`
4. 必要时进入房间手工验证一局

### 4.2 UI 改动

如果改的是：

- `HudScene`
- `MatchScene`
- `globals.css`

建议顺序：

1. 跑 `npm run build`
2. 手工验证至少 1 个房间流程
3. 覆盖相关弹窗、事件提示和棋盘表现

### 4.3 数据结构改动

如果改的是：

- `types.ts`
- `snapshot.ts`
- `schema.prisma`

建议顺序：

1. `npm run db:push`
2. `npm run db:generate`
3. 跑目标测试或构建
4. 打开页面确认快照消费正常

## 5. 补测原则

不是每次都要大量新增测试，但以下情况建议补：

- 新增棋盘格类型
- 新增道具 / 神明 / 牌效果
- 修改回合状态机
- 修改通胀、租金、监狱、破产、自动还款这类关键规则
- 修改托管 / 机器人决策
- 修复曾经出现过的真实 bug

## 6. 当前测试空白

当前仍然存在这些空白区：

- 没有真正的浏览器 E2E
- 没有 API route 层面的集成测试
- 没有 Phaser 场景自动化测试
- 对 SSE 同步链路主要依赖人工验证

这意味着：

- 规则层改动可以较稳定地靠 Vitest 护住
- 表现层与联机链路仍要靠手工回归

## 7. 手工测试建议

每次较大功能合入前，建议最少跑一轮轻量回归：

1. 首页创建房间
2. 加入玩家 / 加机器人
3. 开始游戏
4. 至少掷骰 3 到 5 次
5. 触发 1 个特殊格
6. 打开“更多”里的地产 / 背包 / 事件
7. 验证 HUD 没有遮挡或死按钮

如果涉及专项规则，还要补对应场景，例如：

- 监狱
- 新闻屋
- 机会 / 命运
- 股票停盘
- 道具响应
- 神明附身

## 8. 提交前检查清单

建议提交前至少满足：

- `npm run lint` 通过
- 目标测试通过
- `npm run build` 通过
- 新规则已同步到文档或用例

如果是较大玩法改动，建议额外满足：

- 至少一局手工验证
- 至少一条事件记录 / 快报被验证
- 托管或机器人没有卡在 phase 中

## 9. 如何写新的自动化测试

建议遵守以下原则：

- 测试规则，不测试实现细节
- 输入尽量小，断言尽量明确
- 优先测纯函数和规则模块
- 对需要随机的逻辑，尽量断言“集合完整性”和“结构正确性”
- 如果测试的是 bugfix，测试名要能说明原问题

推荐位置：

- 棋盘与定义：`src/lib/game/*.test.ts`
- 新牌库：`src/lib/game/cards.test.ts`
- 数值规则：对应规则模块旁边
- 托管：`src/lib/game/autoplay.test.ts`

## 10. 测试结果记录建议

如果是较大版本合并，建议在提测说明中记录：

- 自动化测试执行命令
- 构建结果

- 未覆盖风险

可以参考 `test-cases.md` 中的用例编号来描述实际验证范围。
